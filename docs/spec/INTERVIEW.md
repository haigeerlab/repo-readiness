# 需求拷问记录

> 2026-11-19 起。一次一问；每条记下用户原话的结论和对 Spec 的影响。问题来源见 [调研汇总](../research/2026-11-19-research-summary.md) §5。

| # | 问题 | 用户答复 | 对 Spec 的影响 |
| --- | --- | --- | --- |
| Q1 | 技术栈尺子只做建议层，还是允许少数条款升为必须？ | **允许少数必须**（2026-11-19） | 条款格式中技术栈尺子的条款可以是 `must`；建议门槛：只有"用了这个技术就必然该有"的才能是必须，每栈不超过 2 条（这条是我的建议，作为给 `autopr-standard` 的内容约束，待其确认） |
| Q2 | 只服务本组织 12 个仓库，还是将来给组织外用？ | **先只服务本组织**（2026-11-19） | 只认 GitHub、中文输出；三份格式和平台适配层仍按通用标准做，本组织专有内容（autopr 尺子、信箱探针）放在核心之外，不堵死将来对外；多语言、GitLab、插件市场发布都不做 |
| Q3 | 后端 / Go / Rust 技术栈尺子：只留格式位置，还是第一批就写内容？ | **只留格式位置**（2026-11-19） | 第一批技术栈尺子只有前端、Shell 插件两份；用一份玩具技术栈尺子证明"加栈不改代码"；后端 / Go / Rust 候选条款留在调研报告里。附带的建议"Python 检查脚本归入 Shell 插件尺子、不单列"用户未单独表态，按默认处理，Spec 里列为假设 |
| Q4 | "治理成功"以什么为准？ | **试点接进 Auto PR**（2026-11-19），即验收线 C | 第一阶段验收 = 试点仓库达到基础档、接入结论被 Auto PR 准入脚本读取并把信任上限定为 L2。后果：①接口清单 #4（结论格式）、#5（复检与掉档）、#7（脚本放哪）从"尽早"变成**阻塞项**；②进度依赖 `autopr-design` 的准入脚本与中心仓库，Spec 里要写明依赖和对方的交付时间；③试点仓库达到基础档要落地 G2 分支保护、D1 指令文件"先问"边界等改动，每项都要用户逐一同意；④试点仓库要和 `autopr-design` 的试点一致（其设计 P1 写 tier-guard，Q15 建议改 agent-relay），需对齐 |
| Q5 | 技术栈自动检测和仓库声明不一致时以谁为准？ | **以仓库声明为准**（2026-11-19） | 写了 `stacks` 只套声明的栈，没写才用检测结果；不一致时报告列"待确认"，不计分；靠 `readiness.yml` 是 T4（人合并）防止故意不声明 |

拷问结束（5/5）。
